## Yes — but it’s done in the integration, not in the card

The public “short” value like 8425 is treated as the stop code, while the actual unique AT identifier is the stop_id, such as 8425-15788731.

The flow is:

1. Fetch the full GTFS stop list from Auckland Transport:
   https://api.at.govt.nz/gtfs/v3/stops

2. Parse each item into a Stop object:
   - stop_id = the real identifier, like 8425-15788731
   - stop_code = the short sign code, like 8425
   - stop_name = the human-readable name

3. In the search/filter step, it looks for an exact stop-code match first:
   - exact stop code matches are ranked above everything else
   - if the search text matches the stop name or the code, it keeps it
   - it then chooses the matching stop and stores:
     - CONF_STOP_ID = stop.stop_id
     - CONF_STOP_CODE = stop.stop_code

4. Once selected, every later timetable/realtime lookup uses the full stop_id, not the short code.

The relevant logic is basically:
- fetch all stops
- compare the user’s search term against stop.stop_code and stop.stop_name
- pick the best match
- save the chosen stop.stop_id

That is why the integration can resolve 8425 to 8425-15788731 without you manually typing the full ID.

## API calls involved

For stop lookup:
- GET https://api.at.govt.nz/gtfs/v3/stops

For the bus board after a stop is chosen:
- GET https://api.at.govt.nz/gtfs/v3/stops/{stop_id}/stoptrips
- GET https://api.at.govt.nz/realtime/legacy

And it also validates the API key with:
- GET https://api.at.govt.nz/gtfs/v3/versions

So the short code is not converted by a weird local mapping table; it is resolved by loading the AT stop catalog and matching the code against that dataset.
